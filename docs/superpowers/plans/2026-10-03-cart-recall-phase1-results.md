## 三、过程中发现的两个真实 Bug（均已修）

### 3.1 第一个 Bug：选品 SQL 没剔除羊毛账号

**现象**：第一版跑出来的 TOP 15 被长尾商品霸榜——只有 13~16 个加购用户、**0 人成交**、显示「100% 弃购率」。

**根因**：`selectProductAgg` 直接查 `cart_item` 聚合，**没有剔除羊毛账号**。15 个僵尸账号把长尾商品刷进了榜——它们的加购行为污染了商品维度统计。

**两处修复**：
1. **选品聚合改为从 `cart_recall_target` 读**，而不是重新查 `cart_item`。池子已完成全部过滤（有效商品、闲置窗口、异常账号），保证「选品结果」与「待召回人群」**来自同一批数据，口径不会漂移**。
2. **加 `min-abandon-rate: 0.70` 门槛，排序主键从「弃购率」改为「加购未买金额」**。原因：3 个加购用户 0 成交也是 100% 弃购率，排在 300 人加购的商品前面毫无业务意义。改为「先过门槛、再按金额排」，既避开小样本霸榜，又保留大额目标。

> 这个 bug 是**仿真数据跑出来的**——如果直接上真实库、不做过滤，运营会拿着这份榜去发券。**先跑仿真数据的价值就在这里。**

### 3.2 第二个 Bug：漏斗百分比重复计数（自查发现）

**现象**：第一版报告的漏斗写着「砍掉 69.0%」，但逐行相减对不上：9,015 − 3,465 = 5,550，而入池是 7,316。

**根因**：报告里「羊毛账号剔除 3,465 条」是**全表**里羊毛账号的条目总数，但时间窗过滤**已经先砍掉了其中 1,766 条**。
把「全表羊毛条目数」直接放进漏斗做减法，等于对同一批行**重复计数**，百分比被高估了 9.8 个百分点。

**修复**：每一层的剔除量都改为**在本层入口集合内**计算（`dropped_hoard = 通过有效性校验的候选数 − 最终入池数`），
并把「全表 3,465 条中有多少条其实是被时间窗先砍的」作为脚注说明。修正后：

| | 修正前（错） | 修正后（对） |
|---|---|---|
| 羊毛账号剔除 | 3,465（全表） | **1,699**（窗口内） |
| 漏斗合计砍掉 | 69.0% | **59.2%** |
| 逐层相加 = 总数 | ❌ 对不上 | ✅ 17,929 → 7,316 |

> **教训**：漏斗类报表必须做「逐层相加 = 总数」的自校验。
> 一旦某一层的剔除量取自另一个口径的集合（全表 vs 窗口内），数字看起来合理、实际是错的，而且很难靠肉眼发现。
> 这个 bug 不影响任何已落库的代码逻辑（Java 侧的过滤是正确的），**只影响报告口径**——但报告是要拿去拍预算的，所以必须修。

## 四、「走后门」评估：这批人到底触达不到？

> 结论先行：**能触达 90.2%，但「走后门」的四条路里，有三条现在走不通。** 唯一低成本可立即验证的是「站内可见」，真正的外呼/推送需要 Phase 2/3 的基建。

### 4.1 先看数字：90.2% 可触达，但 414 人发券也送不出去

- **可触达用户 3,818 / 4,232（90.2%）**——这个覆盖率**比预期好**，说明「发券送不到」不是主要矛盾。
- 但有 **414 人（9.8%）既无手机号也无 openid**——这批人**任何通道都到不了**，圈进来只能占预算。建议：**发券阶段直接过滤 `reachable = 0`**（对应方案 B，省 10.9 万元）。
- 手机号覆盖 82.1%、openid 覆盖 45.7%——**手机号是主力通道**。

### 4.2 四条「后门」通道逐条评估

| 通道 | 现状 | 能不能走 | 成本/门槛 |
|------|------|------|------|
| **① 短信** | 全项目零代码 | ❌ **现在走不通** | 需短信服务商账号 + 模板报备 + **用户明示同意**（《个人信息保护法》），营销短信合规是硬门槛 |
| **② 微信订阅消息** | 全项目零代码 | ⚠️ **可走，但要资质** | 需小程序已上线 + 订阅消息模板审批；openid 只覆盖 45.7%，只能触达一半人 |
| **③ 站内可见（App/小程序内弹窗/红点）** | 无，但**不需要外部依赖** | ✅ **最可行** | 零外部成本、零合规风险；缺点是要用户主动打开 App 才看得到 |
| **④ 下单页自动抵扣** | 无（`OrderServiceImpl:124` 明确「暂无优惠券 YAGNI」） | ❌ **走不通** | 这属于 Phase 2，要改金额链路（高风险），且**它只是「用券」不是「触达」** |

### 4.3 关键结论

1. **「走后门」≠ 绕过券体系。** 优惠券要能真正核销，**必须**改 `OrderServiceImpl.create()` 的金额计算 + 订单表加 `discount_amount`/`coupon_id` + `pay_record.amount` 取优惠后金额。**这是资损高风险区，绕不过去，只能单独评审。**
2. **触达不是瓶颈，券体系才是。** 90.2% 的覆盖率说明「人有手机号」，但**没有一个通道现成可用**——短信要合规、订阅消息要审批、站内要先有券。
3. **最低成本的第一步 = 站内可见。** 先把圈人结果做成后台可见列表（**已完成**），让运营看到「今天有多少人、哪些商品值得发」，**用真实数据再决定要不要投短信/订阅消息**。
4. **归因能力仍然缺失（最要命）。** 用户一下单，`cart_item` 记录就被删，**券→转化无法归因**。建议 Phase 2 一开始就补 `cart_add_log` 加购流水表——**它只能记录埋点之后的行为，晚一天少一天数据。**

## 六、怎么复跑这份数据

```bash
# 需要本地 MySQL 8（默认 localhost:3306，root）
python3 sql/demo/gen_recall_demo.py
```

脚本会：① 重建隔离库 `spring_shop_demo`；② 应用真实迁移脚本 V1/V2/V3/V6/V7；③ 生成 6000 用户 / 60 商品 / 240 SKU / ~1.8 万购物车条目 / ~1.8 万订单；④ **跑与 Java 完全相同的 SQL**，输出上面 7 节报告。

> 脚本不会碰你的 `spring_shop` 主库，全部在 `spring_shop_demo` 里操作。
