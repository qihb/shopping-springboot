# 基础框架评估与多人协作方案

> 目的：评估 spring-shop 基础框架完整性，明确多人并行开发业务前需补齐的协作基础设施，并给出落地路线图。

## 一、当前框架能力盘点（已完成）

| 类别 | 内容 | 状态 |
|------|------|------|
| 多模块架构 | common / user / admin / web，父 POM 统一依赖管理 | ✅ |
| 统一响应 | `Result` / `ResultCode` / `PageResult` / `PageQuery` | ✅ |
| 异常体系 | `BusinessException` + 全局兜底（业务/参数/类型/未知） | ✅ |
| 持久层 | MyBatis-Plus：分页、乐观锁、逻辑删除、自动填充、驼峰映射 | ✅ |
| 序列化 | Jackson 统一 `LocalDateTime` 格式（坑点已处理） | ✅ |
| 安全认证 | Spring Security 双过滤链 + 无状态 JWT + `userType` 区分前后台主体 + 401 统一 JSON + `UserContext` | ✅ |
| 后台权限中心 | 管理员登录、RBAC、角色/菜单管理、`@PreAuthorize` | ✅ |
| Redis 能力 | 登录失败锁定、token 黑名单主动失效 | ✅ |
| 操作审计 | `@OperationLog` + AOP 落库 | ✅ |
| 数据库迁移 | Flyway V1~V3（用户/商品/订单全套表），baseline 兼容旧库 | ✅ |
| 多环境 | dev / prod 配置分离，密码与密钥全部环境变量化 | ✅ |
| 日志 | logback 按天滚动 + error 归档 + 环境差异化 | ✅ |
| API 文档 | springdoc 已引入（Swagger UI + @Tag/@Operation） | ✅ |
| 提交规范 | `commit-msg` 钩子校验中文提交格式 | ✅ |
| 代码规范 | AGENTS.md：分层红线、命名、注释、接口约定 | ✅ |
| 远程仓库 | `github.com:qihb/shopping-springboot` | ✅ |

**结论**：框架层面已经具备“单体电商后端 + 管理后台”的生产化基础能力。当前更适合继续保持单仓多模块，优先完成商品 / 购物车 / 订单等主业务，而不是过早把前后台后端拆成两个独立项目。

## 二、多人协作前必须补齐的高优先级事项

### 1. 自动化测试（现状：零测试，最大风险缺口）

多人并行时改 common 或某模块很容易踩到别人的功能，没有测试回归只能靠手点。

| 层级 | 内容 | 技术选型 |
|------|------|----------|
| 单元测试 | Service 层纯逻辑（唯一性校验、密码校验、状态判定） | JUnit 5 + Mockito |
| 集成测试 | Controller 全链路（注册→登录→带 token 访问 /me） | `@SpringBootTest` + MockMvc |
| 数据库 | 内存库跑 Flyway，不依赖本地 MySQL | H2（MySQL 兼容模式） |

> 选 H2 而非 Testcontainers：学习项目追求简单可复现，H2 一条配置即可在本地与 CI 中跑同样的测试；`application-test.yml` 单独配置，不污染 dev 环境。

### 2. CI 持续集成

GitHub Actions 最小流水线：push / PR 触发 → JDK 21 → `mvn -B verify`。配合 GitHub **分支保护规则**：main 不允许直接 push，必须走 PR 且 CI 通过。

### 3. 分支与评审工作流

```
main（受保护，随时可发布）
 └── feature/<模块>-<功能>   # 如 feature/product-sku-list
       └── PR → main（CI 通过 + 至少 1 人评审）
```

- 每个 PR 只做一个功能（符合 AGENTS.md "小步提交"）
- Maven 多模块天然隔离，商品/订单/购物车各开分支互不阻塞

### 4. 协作冲突协调约定（隐性风险点）

模块间物理隔离，但以下三处是全局共享、多人会撞车：

| 共享点 | 冲突风险 | 约定 |
|--------|----------|------|
| `ResultCode` 错误码 | 各模块都在加错误码 | 按段位分配：用户 1000 / 商品 2000 / 购物车 3000 / 订单 4000；公共 0~99 |
| Flyway 脚本 | 多人同时提交 V4 | 新脚本不修改已提交脚本，PR 冲突先合小的 |
| `spring-shop-common` | 全员依赖，改动影响面大 | 变更必须过评审；新增公共能力先讨论再动手 |

## 三、框架可补充的增强项（中低优先级，按需）

| 增强项 | 说明 | 优先级 |
|--------|------|--------|
| OpenAPI 安全配置 | Swagger UI 中标注 Authorize 按钮，调试带 token 更顺 | 中 |
| 环境统一 | `.mvn/wrapper` + `.java-version`，保证全员 JDK/Maven 一致 | 中 |
| seed 数据 | 商品分类/演示商品初始化脚本（开发便利） | 中 |
| 通用工具封装 | `BeanUtils.copy` 封装、集合/断言小工具 | 低 |
| 接口版本控制 | `/api/v1` 前缀 | 低，暂不做 |
| Redis 缓存/限流 | 商品详情缓存、接口防刷 | 业务跑通后再加 |

## 四、当前阶段的架构取舍：一个项目还是两个后端项目？

### 方案 A：单仓多模块（当前做法）

- 形式：`spring-shop-user` + `spring-shop-admin` + `spring-shop-web`
- 优点：
  - 公共能力复用成本最低
  - 商品/订单/用户/后台共用同一套模型时协作更顺
  - 适合当前阶段快速演进
- 缺点：
  - 最终发版仍是整体发版
  - 边界靠模块设计和代码规范来保证

### 方案 B：拆成两个后端项目

- 形式：前台用户站点后端一个项目，后台管理站点后端一个项目
- 优点：
  - 独立部署、独立扩容、独立发版
  - 网络隔离和权限边界更强
- 缺点：
  - 基础设施、认证、日志、配置维护成本翻倍
  - 商品、订单、用户等核心数据的跨项目协作更重

### 当前建议

对本项目，更推荐：

1. **后端继续保持一个仓库、多模块**
2. **前端页面拆成两个独立项目**（商城 Web / 管理后台 Web）
3. **等主业务成熟后**，再判断后台是否值得单独拆服务

## 五、后续业务场景前瞻（电商典型，开发时按需设计）

| 场景 | 技术点 | 触发时机 |
|------|--------|----------|
| 库存扣减并发 | 乐观锁（已配置）→ 进阶分布式锁 | 下单模块 |
| 下单防重/幂等 | 唯一订单号 + 防重校验 | 订单模块 |
| 订单超时未付取消 | 定时任务（Spring `@Scheduled`） | 订单模块 |
| 商品详情热点 | 本地缓存 → Redis | 商品模块跑通后 |
| 支付回调 | 异步回调 + 状态机校验 | 后续扩展 |
| 接口防刷 | 简单限流拦截器 | 上线前 |

> 这些都不需要提前搭建，单体架构下按需引入即可，避免过早复杂化。

## 六、落地路线图

```
阶段 1：协作地基（已完成）
  ① 测试基座：application-test.yml + H2 + 用户/后台集成测试
  ② GitHub Actions CI + main 分支保护
  ③ 错误码段位 / Flyway 约定写进 AGENTS.md

阶段 2：生产化后台（已完成基础版）
  ① admin 模块拆分
  ② 双过滤链 + ADMIN/USER token 区分
  ③ RBAC + Redis 登录加固 + 操作审计

阶段 3：核心业务落地（下一步重点）
  商品模块 ← 购物车模块 ← 订单模块，各开 feature 分支并行

阶段 4：增强（业务跑通后按需）
  缓存 / 定时任务 / 限流 / 接口版本化 / 支付
```

**一句话结论**：框架已 90% 完成，补上「测试 + CI + 分支工作流 + 共享点约定」4 块即可放心多人并行；不建议提前堆 Redis、分布式事务等重型设施。
