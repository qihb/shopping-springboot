### 实验二结果（29 个工具，写链路 10 步全绿）

- 接入地址三处坑（计划里给的地址是错的）：
  1. `h=` 必须是 **JSON 对象**（`{"Authorization":"Bearer xxx"}`），README 写的 `header:value` 与实现不符；
  2. `f=` 分隔符是**分号**不是逗号（`ParseFilterDSL` 按 `;` 切分）；
  3. 分号必须编码成 `%3B` —— Go 的 `url.ParseQuery` 遇到裸 `;` 会**整条丢弃该参数**，
     过滤会静默失效、admin 接口漏出去。
- 过滤器生效：`+/api/**;-/api/admin/**` → 29 个工具，无 admin 接口。
- **写接口的 `requestBody` schema 被 mcp-link 丢成空对象**（OpenAPI 里定义完整，是它的缺陷）→
  AI 无法从工具描述拼出写接口入参，写链路只能靠人工补文档。这是实验二最大的可用性缺陷。
- 写链路 10 步实测通过：加购 → 建地址（先故意传错手机号）→ 下单 → 支付 → 复查。
  错手机号返回 `HTTP 200 + {"code":400}`，符合项目「业务失败走 200 + 业务码」的约定。

### 顺带发现的后端真 bug（高优先级，未修）

**下单后购物车 Redis 缓存不失效。**
- 现象：下单成功、库存已扣、DB 里 `cart_item` 行已物理删除，但 `GET /api/cart` 仍返回该条目且 `checked=true`。
- 证据：`SELECT * FROM cart_item WHERE user_id=5` → 空；`redis-cli HGETALL cart:5` → `64 → 4|3|1`。
- 根因：`OrderServiceImpl.create()` 直接用 `cartItemMapper.delete(...)` 删行，**绕过 `CartServiceImpl`**，
  因此只失效了商品详情缓存，**从未失效 `RedisKeys.cart(userId)`**；而 `CartServiceImpl` 自己的
  删除路径（delete/deleteChecked/clear）都是会失效的。
- 影响：TTL 是 7 天滑动过期，用户继续操作就不断续期，脏数据可能长期不自愈；前端表现为
  「下单后购物车没清空且仍勾选」，点结算才报「购物车没有勾选商品」。
- 价值：**只读链路测不出这类问题** —— 实证了计划里「写链路才是方案选型的核心依据」这个判断。
- **→ 下次可做：修这个 bug**（在 `OrderServiceImpl.create()` 删完购物车行后补一行失效
  `RedisKeys.cart(userId)`，并补一条集成测试覆盖「下单后购物车列表为空」）。

### 实验四的两个新坑

1. **`@Tool` 不会自动注册**：只给 Bean 加 `@Tool`，`tools/list` 返回 **0 个工具且不报任何错**。
   必须显式提供 `ToolCallbackProvider` Bean（`MethodToolCallbackProvider.builder().toolObjects(...)`）。
   别和 MCP 专用的 `@McpTool` 混淆（那个才由 `annotation-scanner` 默认自动扫）。
2. **MCP 响应不走项目的 Jackson 配置**：同进程 A/B 对照 ——
   HTTP `GET /api/products` 返回 `"2026-10-02 09:42:13"`，
   MCP 工具 `searchProducts` 返回 `[2026,10,2,9,42,13]`（数组）。
   `JacksonConfig` 的 `LocalDateTimeSerializer` 对 Spring AI 内部 ObjectMapper 不生效。

### 结构性限制（重要）

**进程内方案做不了写链路**：工具直接调 Service，不过 HTTP 过滤链 → 拿不到 JWT 里的 `userId`。
把 token 当工具参数传等于把鉴权交给模型，不可接受。所以进程内只能只读。
→ **结论：实验二（能写、schema 差）与实验四（schema 准、不能写）是互补关系，不是替代关系。**

## 追加：Excel 框架盲区 #2 修复（静默导出全量）

接着用户第三次 `继续`，按 `2026-10-03.md` 记的建议顺序，先排最危险的第 2 条。

### 缺陷复核：机制完全成立

`ExcelTaskServiceImpl.writeParams` 捕获序列化异常后 `return null` → 任务行 `params` 为 SQL NULL →
后台 `ExcelTaskContext.params()` 读到 null 就 `return null` → `ExcelExportSupport.export` 把 null
当查询条件传给 fetcher → 业务侧 `null` = 「无筛选」→ **导出整张表**，
而任务状态是「成功」、文件能下载。**没有任何报错信号**。

### 决定修复方式的关键事实

**四个生产导出服务全都写了 `query == null ? new XxxQuery() : query`**
（`ProductExportServiceImpl:52`、`AdminUserExportServiceImpl:45`、
`OperationLogExportServiceImpl:46`、`OrderExportServiceImpl:50`）。
⇒ 生产路径下 `writeParams` **永远拿不到 null**
⇒ `params` 列是 SQL NULL **只可能**来自「序列化失败被吞掉」。
⇒ 所以「`query == null` 返回 null」这个分支**必须保留**（那是显式的不筛选语义），
   只把「catch → 返回 null」改成「catch → 抛异常」。

### 改动（TDD：先红后绿）

| 文件 | 改动 |
|---|---|
| `ResultCode` | +`EXCEL_TASK_PARAMS_INVALID(47, ...)`（公共段 47 之前空着） |
| `ExcelTaskServiceImpl.writeParams` | `catch → log.warn → return null` 改为 `catch → log.error → throw BusinessException` |
| `ExcelTaskContext.params` | 空 params 时补 INFO 日志；javadoc 写明「null 只表示显式不筛选」契约 |
| `ExcelTaskService.createExportTask` | javadoc 补 `@throws` |
| `ExcelTaskServiceImplTest`（新建） | 2 用例：正常落库；序列化失败抛 47 且 `never()).insert(...)` |

`writeParams` 在 `insert` **之前**执行 ⇒ 抛异常时任务行根本没落库，无脏数据要清理。

**踩到的编译坑**：`verify(mapper, never()).insert(any())` 编译不过 ——
MyBatis-Plus 3.5.17 的 `BaseMapper` 同时有 `insert(T)` 和 `insert(Collection<T>)`，
裸 `any()` 重载歧义。必须写 `any(ExcelTask.class)`。

**没做的**：没把 `params()` 改成「空就抛」。那会否掉 `ExcelExportSupportTest`
里 `contextFor(null)` 的既有契约（4 个用例靠它表示「无条件导出全量」），属于把
「危险默认值」问题混进本条，超出范围。

### 验证

- `mvn -pl spring-shop-common test` → 17 用例全绿
- `mvn test`（全 reactor）→ **101 用例 0 失败，BUILD SUCCESS**

全仓**无任何显式 poi / poi-ooxml 声明**（由 fesod 传递引入 POI 5.5.x，重复声明会 `NoSuchMethodError`）。

**两层架构**：
1. 底层纯技术层（`common/excel/`）：`ExcelSupport`（SAX 流式读，`readDefaultReturn(STRING)` 统一读成字符串）
   + `ExcelStreamWriter`（分批写）+ `ExcelReadOptions` + `ExcelRow` + `ImportError`。
   **不含任何业务语义**（表头是否正确、字段是否必填都由业务侧做）。
2. 上层异步任务框架（`common/excel/task/`）：`excel_task` 任务表（V8）+ 独立线程池
   `excelTaskThreadPool`（核心 2 / 最大 4 / 队列 50 / **AbortPolicy**）+ `ExcelFileStorage`
   （落盘 `{tmp-dir}/{yyyyMMdd}/{taskNo}.{ext}`）+ 进度/失败明细缓冲写。

**两个导入的解析策略是刻意不同的**（这是设计要点，不是不一致）：
- **管理员导入**（`AdminUserImportServiceImpl`）：`streamRead` **真流式**，边读边攒批，
  峰值内存 = 一批 500 行 + Fesod 缓冲，与文件行数无关；用户名查重**按批做**（不预读全文件）。
- **商品导入**（`ProductImportServiceImpl`）：`readAll` 全量驻留内存，因为要**按商品名称跨行聚合成 SPU**；
  上限 `max-import-rows: 100000`（十万行 ExcelRow 约几十 MB，是「按名称聚合」的必要代价）。

**落库策略（两者一致）**：`TransactionTemplate` 而非 `@Transactional`（执行体在异步线程里自调用不走代理）
→ **批内一个事务、批间独立**，整批失败降级为逐组/逐行重试 → 实现「**部分成功**」语义。
