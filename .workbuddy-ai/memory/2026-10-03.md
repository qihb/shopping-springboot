## 定时任务平台化 + 重跑机制 — 技术方案（未落地代码，待用户拍板）

**用户指令**：「后面还会有更多任务，给我出一份相关的技术报告选项，支撑后面更多任务跑，还要有任务重跑机制」。

**产出**：`docs/superpowers/plans/2026-10-03-scheduled-task-platform-options.md`（7 个调度方案对比 + 重跑机制设计 + 待拍板 7 项）。

**关键调研结论（复用价值高）**：
- **两个定时任务能力集完全不同**，证明基础设施缺抽象层：
  | | `OrderTimeoutTask`（62 行） | `CartRecallTask`（197 行） |
  |---|---|---|
  | 分布式锁 | ❌ 无 | ✅ Redis 锁 |
  | 任务日志 | ❌ 只有 log.error | ✅ stats_task_log |
  | 开关 / 手动触发 | ❌ 无 | ✅ 有 |
  新增一个任务约 **150 行样板代码**，业务逻辑只占 ~20 行。
- **本方案的核心认知：不是所有任务都能重跑**。必须先分类：
  A 全量重建型 / B 按天快照型 / C 状态机推进型（均可重跑）vs **D 副作用型（发券/发短信，默认禁止重跑）**。
  四种幂等策略：`DELETE_INSERT` / `UPSERT` / `CONDITIONAL` / `NONE`。
- **`bizDateAware` 是最关键的开关** —— 任务签名必须统一为 `execute(LocalDate bizDate)`，
  不参数化业务日期就只能重跑「今天」，历史补数无从谈起。这是当前设计最大的结构性缺陷。
- **六道重跑护栏**：bizDate 必传 / 唯一键 `uk_task_biz_attempt` 防并发 / 窗口 ≤30 天 / 每日 ≤3 次 / 不可重跑任务拒绝 / `task:run` ≠ `task:rerun` 权限分离。
- **自动重试只对瞬时异常生效**：`QueryTimeoutException`/`TransientDataAccessException`/死锁/Redis 抖动 → 重试；
  `BusinessException`/参数错误/脏数据 → **不重试**（重试也是白试）。退避 1min→5min→15min，上限 3 次。
- **「产出 0 行」告警最容易被忽略但最有价值** —— 任务「成功」了但没产出数据，比跑失败更隐蔽。
- **推荐方案 B（自研轻量层）**：单体应用 + 任务数 10 上下，上 XXL-JOB 的运维成本 > 收益。
  自研必须克制，只做统一锁/日志/重跑/告警四件事；触到编排/分片/GLUE 边界就该迁 XXL-JOB（触发条件：任务数 >15）。
- **`OrderTimeoutTask` 迁移时应保持不加锁**（声明 `lockStrategy = NONE`）—— 它 fixedDelay 60s、处理量小、
  `systemCancel` 是条件更新天然幂等，加锁反而可能因锁竞争影响取消时效。**这也验证抽象层必须支持「按任务选策略」**。
- **`OrderTimeoutTask` 是 `bizDateAware = false` 的「持续扫描」型** —— 抽象层必须同时容纳「按天跑批」和「持续扫描」两种形态，
  否则说明抽象错了。

**待拍板 7 项**：调度框架 / 锁实现（手写 Redis vs ShedLock）/ 不可重跑默认值 / 重跑窗口 / 告警通道（需 webhook 地址）/ 是否本期迁 OrderTimeoutTask / 模块归属（建议新建 `spring-shop-task`）。

**澄清结论**（AskUserQuestion）：用户管理指**后台管理员账号**（非前台会员）；导入策略选**部分成功**。

**交付**：

- 个人中心改密 `/api/admin/profile/password`
- 商品导入 `/api/admin/products/import` + 模板；管理员导入 `/api/admin/users/import` + 模板
- 新增 `spring-shop-common/.../common/excel/`（ExcelSupport / ExcelRow / ImportError / ExcelReadException，POI 薄封装）

**过程中发现并修掉的 4 个真问题（复用价值高）**：
1. **`AdminDataInitializer` 幂等性缺陷**：原逻辑「`admin_user` 非空就整体跳过」→ **新增的菜单/权限永远进不了老库** → 新加的 `@PreAuthorize` 标识永久 403，且现象极难定位。改为以 `menu.permission_code` 为幂等键**逐项 find-or-create**，`ensureRoleMenus` 只增不减。
2. **审计脱敏漏字段**：`OperationLogAspect` 原来精确匹配 `"password"`，`oldPassword`/`newPassword` 会把明文密码写进 `operation_log`。改为正则 `"([^"]*password[^"]*)"\s*:\s*"[^"]*"`，并排除 `MultipartFile` 参数。
3. **禁用不生效**：JWT 无状态，禁用管理员后已签发 token 仍可用到过期。`AdminJwtAuthenticationFilter` 本来就每次请求回查 `loadUserByUsername`，在 `AdminUserDetailsService` 里加 `status != 1` 抛 `UsernameNotFoundException` → 过滤器 clearContext → 401，实现**权限实时性**（代价：每请求一次查库，后台低频可接受）。
4. **`@PreAuthorize` 拒绝被吞成 500**：方法级鉴权异常发生在 Controller 调用期，不经过 `ExceptionTranslationFilter`，被 `GlobalExceptionHandler` 的 `Exception` 兜底变成「系统内部错误」。新增 `spring-shop-web/.../web/exception/SecurityExceptionHandler`（`@Order(HIGHEST_PRECEDENCE)`，`AccessDeniedException` → HTTP 403 + `Result.fail(FORBIDDEN)`）。**放 web 不放 common**，因为 common 刻意不依赖 spring-security。

**踩坑/约定（重要）**：
- **`uk_sku_code` 唯一索引不排除逻辑删除行** → 导入前的占用查询必须用裸 SQL（`ProductSkuMapper.selectOccupiedSkuCodes`），用 lambda 查询会漏掉已删行，最终 insert 撞唯一键抛 500。
- **`admin_user` 逻辑删除 + `username` 唯一索引** → 删掉的用户名永久占用，且会让初始化器 `ensureAdminUser` 撞唯一键。**故不提供管理员删除接口**，用「停用」等价替代。
- **唯一键「先校验后占坑」**：SKU 编码/用户名要在**所有字段校验通过之后**才标记占用，否则「价格写错而失败的行」会把编码锁死，同文件里后面的合法行被误报重复。
- **先建完 SKU 再插 SPU**，否则产生「有 SPU 无 SKU」的空商品。
- **组级失败要逐行铺开**（商品按名称分组，分类解析失败 → 每行都给原因）。
- **价格精度要显式拒绝**：`DECIMAL(10,2)` 会静默四舍五入，导入侧校验 >8 位整数 / >2 位小数直接报错。
- **`ExcelSupport.read` 跳过表头行且不校验列名**（改测试表头不影响解析，但测试表头应与模板保持一致以防将来加校验）。
- **`BusinessException` 没有 `(Integer)` 单参构造**，只有 `(String)` / `(ResultCode)` / `(Integer, String)`。
- **`mvn -pl a,b` 不带 `-am` 会用 `~/.m2` 里的旧 common jar** → 报「程序包不存在」。要么带 `-am`，要么跑全量 reactor。

## 真机启动验证：发现并修复 logback 默认 profile 无日志的 bug

**动机**：MockMvc 的 `multipart()` 是伪造请求，**不经过 Tomcat 的真实 multipart 解析**，所以
`spring.servlet.multipart.max-file-size` 与 `MaxUploadSizeExceededException` 这条路径其实没被测过。
想用「真启动 + curl」补这个缺口。

**结果**：E2E 没做成，但**意外挖到一个真 bug**。

**发现的 bug**：`spring-shop-web/src/main/resources/logback-spring.xml` 里
`<root>` **只在 `<springProfile name="dev">` 和 `<springProfile name="prod">` 内定义**，
没有兜底分支。

- Logback 在「找到了配置文件但没有任何 `<root>` 生效」时**不会退回默认控制台输出**，
  而是根 logger 一个 appender 都没有 → **应用照常启动，但一行日志都不打印**。
- 配置本身只打印 `Appender named [CONSOLE] not referenced` 这种极易被忽略的告警。
- 实测：用 `--spring.profiles.active=test` 启动 → 退出码 1，日志文件只有 14 行（全是 logback 内部告警 + banner），
  **完全看不出失败原因**。加上兜底段后同样的启动立刻打印出 18 行日志，一眼看到
  `Failed to determine a suitable driver class`（因为 test profile 没有数据源）。

**修复**：加一段取反兜底 `<springProfile name="!dev &amp; !prod">`，挂 CONSOLE+FILE+ERROR_FILE。

- **关键点：不能在 `<configuration>` 里直接再写一个 `<root>`** ——
  Logback 对多个 `<root>` 是**累加 appender**而非覆盖，会让 dev/prod 下日志打印两遍。
  实测确认修复后 `Started SpringShopApplication` 只出现 1 次（无重复挂载）。
- prod 复测：控制台仍 0 行 Spring 日志（只写文件），行为未变。

**附带确认**：`spring.profiles.active` 默认是 **`dev`**（`application.yml` 的 `${SPRING_PROFILES_ACTIVE:dev}`）；
数据源只在 `application-dev.yml` / `application-prod.yml` 里定义，`application.yml` 本身不含 `spring.datasource`。
`application-test.yml` 在 `src/test/resources`（测试作用域，**不进 jar**），所以 `test` profile **不能**用来跑 jar。

**环境限制（重要）**：沙箱里**无法长期运行服务** —— 后台 java 进程约 3s 就被回收，`ps` 也是
`operation not permitted`。可行做法是**把「启动 + 探测 + kill」全部放进同一条命令**（前台 `&` + `sleep` + `kill`）。
另外 `curl localhost` 走沙箱代理，端口没监听时返回 `upstream connect failed: Connection refused (os error 61)`。

**注意**：本机 6001 端口上有**用户自己正在运行的实例**（`/api/health` 正常），不要 kill；
验证要用别的端口（6095~6099），并且**不要**拿 `dev`/`prod` profile 去连用户的真实 MySQL 写数据。

**验收**：修复后 `mvn clean verify` → **BUILD SUCCESS，243 tests，0 failures**。
**文档**：`README.md` 新增「关于 profile（重要）」+ 修正「admin_user 表为空时」这句已过时的说明；
`AGENTS.md` 新增「日志与 profile 约定（强约束）」。

## 真机 multipart 测试：抓出 max-swallow-size 导致超限提示送不出去

**怎么在沙箱里做到「真实 HTTP」**：`mvn test` 是可以正常跑的，所以用
`@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate` 就能在 surefire JVM 内
起一个**真实 Tomcat**，从而覆盖 MockMvc 结构上覆盖不到的东西
（MockMvc 的 `multipart()` 构造 `MockMultipartHttpServletRequest`，**完全跳过容器的 multipart 解析**）。
—— 这比「起独立进程 + curl」更可行（后者在沙箱里跑不住）。

**新增**：`spring-shop-web/src/test/java/com/springshop/web/ProductImportMultipartIntegrationTest.java`（4 用例）。

**抓到的 bug**：上传超过 `max-file-size` 的文件时，客户端拿到的是
`java.io.IOException: chunked transfer encoding, state: READING_LENGTH` / `Broken pipe`，
**而不是** `GlobalExceptionHandler` 那句「上传文件过大，请拆分后分批导入」。

- 根因：**Tomcat `maxSwallowSize` 默认只有 2MB**，而 `spring.servlet.multipart.max-request-size` 是 10MB。
  被拒绝的请求体一旦超过 2MB，Tomcat 无法吞掉剩余字节 → 直接断连 → 响应根本没机会写回。
  也就是说**光配 `max-file-size` 是不够的**，之前文档里那句「超限由 GlobalExceptionHandler 转成可读提示」在真机上不成立。
- 修复：`application.yml` 加 `server.tomcat.max-swallow-size: 12MB`（略大于 max-request-size）。
  修复后 4 个用例全绿，友好提示正常返回。

**这个类两个刻意的写法（都很关键）**：
1. **不加 `@Transactional`** —— 请求跑在 Tomcat 工作线程，测试事务回滚不了服务端事务，
   加了只是错觉。所以该类**只做只读或必然失败的操作**，不写库：`jdbc:h2:mem:spring_shop_test`
   在同一 surefire JVM 内是**共享**的，写脏会串到其他测试类。
2. 上传用 `ByteArrayResource` 必须**覆写 `getFilename()`**，否则该 part 退化成普通字段，
   服务端不会按「上传文件」处理。

**验收**：`mvn clean verify` → **BUILD SUCCESS，247 tests，0 failures**（web 模块 82 → **86**）。
**文档**：`AGENTS.md` 新增「#### 2. 需要真实 Servlet 容器时」（并把原 2/3/4 顺延为 3/4/5）、
HTTP 状态码表补 `max-swallow-size` 前提说明；`docs/product-module.md` §6 与 §8.2 同步补上该前提与新测试类。

### Fesod 三个必须记住的坑（都靠 `javap` 读真实字节码确认，不是猜的）

1. **`builder.head(List<List<String>>)` 是「列优先」** —— 传 `List.of(headers)` 会写出一个
   「3 行 × 1 列」的转置表头。已在 `ExcelStreamWriter.toColumnMajorHead()` 里转置修掉。
2. **自动探测文件类型会静默退化成 CSV** —— 损坏/垃圾字节不报错，直接读成 0 行。
   必须显式 `excelType(...)`。
3. **一行都没写时 Fesod 不创建 sheet** —— 回读报 `Can not find any sheet!`。
   所以「空集合也要走一遍 `write`」才能保住表头（导出 0 行时尤其重要）。

### 其它踩过的坑（按发现顺序）

- **`fesod-sheet` 会传递引入 POI 5.5.x**：不要再单独声明 `poi-ooxml`，否则 `NoSuchMethodError`。
- **bean 名撞车**：`@Component ExcelTaskExecutor` 按类名推导出的 bean 名就是 `excelTaskExecutor`，
  和 `@Bean(name="excelTaskExecutor")` 直接 `BeanDefinitionOverrideException`（Boot 默认禁止覆盖）。
  已改名 `excelTaskThreadPool`。
- **`@MapperScan("com.springshop.**.mapper")` 会关掉 MyBatis 的 `@Mapper` 注解自动扫描** ——
  mapper 接口必须落在以 `mapper` 结尾的包里，所以 `excel/task/mapper/` 是必需的，不是风格问题。
- **Java 包名与目录不一致**：文件放在 `.../task/impl/` 但写 `package ...excel.task;`，
  编译产物落到 `task/`，残留旧 class → `ConflictingBeanDefinitionException`。
  **改包名后必须 `mvn clean -pl <module>`**。
- **异步线程拿不到 `UserContext`**（ThreadLocal 不传播）→ 管理员 id 必须在**受理时**就捕获。
- **`TransactionTemplate` 而不是 `@Transactional`**：执行体是异步线程里的自调用，不走代理。
  落库做成「批级事务 + 批内原子 + 批间独立」，批失败后**逐组/逐行重试**，
  把唯一键冲突精确降级到某一行，而不是整单回滚。

### 顺手挖出的 3 个**真实生产 bug**（都是写单测时被断言逼出来的）

1. 商品导入：所有行都在「按名称分组」阶段失败时，任务以「处理 0 行 / 失败 0 行」收场
   —— `recorder.flush()` 被写在 `if (!pending.isEmpty())` 里，且 `failRows` 被预置+累加双计。
   修法：去掉预置，末尾**无条件** `flush()`。
2. 管理员导入：`flush()` 只在 `accept()` 里上报进度，即**落库之前**上报，
   导致 successRows/failRows 永远是 0。修法：抽出 `persistWithFallback(...)`，
   在 `flush()` 末尾统一 `reportProgress(...)`。
3. 管理员导入：`encodePasswords` 在本批没有显式密码时提前 `return`，
   留空的行带着 `null` 密码写库 —— 「用默认密码」变成了「密码为空」。
   修法：去掉提前返回。

## 追加：导入导出实现的设计复盘（用户要求解释设计 + 找盲区）

用户问「解释一下你的导入导出代码实现设计，解决了哪些问题，怎么解决的，还有没有没考虑到的场景」。
把 `ExcelTaskExecutor` / `ExcelTaskServiceImpl` / `ExcelTaskContext` / `ExcelExportSupport` /
`ExcelFileStorage` / `ExcelSupport` / `AdminUserImportServiceImpl` 完整重读了一遍。

### 顺手发现的两处**代码缺陷**（本轮只记录，未修）

1. **`ExcelTaskExecutor` 类注释与实现相反**。类注释写「导入先落盘再建任务行（顺序不能反——
   先建行后落盘，落盘失败会留下一个永远跑不动的任务）」，但代码是
   `createImportTask` → `saveImportFile` → 失败时 `markFailed`，**先建行再落盘**。
   注释描述的是另一套设计。而且注释担心的场景在当前实现里**依然会发生**：
   建行与落盘之间进程被杀 → 留下 PENDING 且 `file_path` 为 null 的任务，没人派发它，
   只能等 24 小时后的 `failStaleTasks` 兜底。→ **应改注释**（当前设计本身没错，
   因为文件名依赖 taskNo，必须先生成 taskNo）。
2. **`submitImport` 的异常兜底用错了错误码**：catch 块抛
   `ResultCode.EXCEL_TASK_BUSY.getCode()`（43 =「系统繁忙，任务排队已满」）
   但文案是「文件保存失败，请重新提交」。前端若按 43 做「稍后重试」的引导就会误导。
   → 应新增一个「文件保存失败」的码，或复用 `SYSTEM_ERROR`。

### 已识别的盲区（**尚未修**，按严重度排序；做完要回头标注本条）

**高（会伤数据 / 静默出错）**

1. **导入是「纯新增」，重跑即翻倍**。没有批次/幂等概念：商品导入重传同一文件会再建一套
   SPU+SKU（只有撞 SKU 唯一键的行会失败）；管理员导入则表现为「整批全红：用户名已存在」。
   缺「同名即更新」的 upsert 语义，也缺「本次导入批次 + 撤销」。
2. **`params` 序列化失败 → 静默导出全量**。`ExcelTaskServiceImpl.writeParams` 捕获异常
   返回 null → `ExcelTaskContext.params()` 返回 null → fetcher 收到 null → 业务侧按
   「无筛选」处理 → **导出整张表**。用户以为导的是筛选结果。危险且无声。
3. **导出分页是 OFFSET（`Page<>(current, pageSize)` + `current++`）**，不是 keyset。
   十万行导出期间若有并发插入/删除，结果集会漂移 → **重复行或漏行**。
   建议改 `WHERE id < lastId ORDER BY id DESC LIMIT n`。
4. **表头内容完全不校验，按列下标取值**（`COL_XXX = 0/1/2...`）。
   用户把「副标题」和「主图URL」两列对调，导入照样成功，只是数据串了。没有模板版本号。

**中（体验 / 正确性边界）**

5. **没有取消任务**。提交错了只能等它跑完（可能几分钟），期间 `assertNotRunning` 还拦着重提。
6. **`assertNotRunning` 是 check-then-act**，多实例部署下有竞态（两个实例可能都通过检查）。
   没有唯一索引或分布式锁兜底。注释里对清理任务论证过「不加锁因为幂等」，但这个竞态没被讨论。
7. **失败明细截断无提示**。`max-error-rows=10000`，超出部分只打一行 warn 日志，
   用户在任务详情里看不到「还有 N 条未记录」。
8. **`markSuccess` / `markFailed` / `markRunning` 都是无条件 UPDATE**（`WHERE task_no = ?`），
   会覆盖清理任务写的终态。极端场景：任务跑超 24 小时 → 被 `failStaleTasks` 判失败 →
   跑完又被 `markSuccess` 改回成功。应改成带状态条件的 CAS。
9. **导出进度没有分母**。`total_rows` 只在 `markSuccess` 时才写，导出过程中
   `resolveProgress` 恒返回 1（`total <= 0 → processed > 0 ? 1 : 0`）。前端进度条无意义。
10. **`excel_task` / `excel_task_error` 无限增长**。只清磁盘文件（`clearFilePath`），
    从不清任务记录。一年下来明细表会膨胀。

**低**

11. 下载不支持 Range / 断点续传，慢客户端一直占着 Tomcat 线程。
12. 受理阶段在 HTTP 线程里同步落盘（当前上限 5MB 还好；放宽文件上限时这里会先成瓶颈）。
13. 跨管理员并发同一业务时，SKU 查重基于各自开始时的快照，冲突只在落库暴露，
    报错文案是「落库失败：xxx」而不是「SKU 编码已存在」。
14. 商品导入「组内部分失败」的语义：3 行里 1 行 SKU 重复，SPU 仍会建、另 2 个 SKU 会进去；
    用户重传修正版时那 2 行又报「已存在」。没有「整组原子」。

> 若用户要修，建议顺序：2（静默全量，最危险）→ 1（重跑翻倍）→ 4（串列）→ 3（分页漂移）→ 8（状态覆盖）。

### 补充：轮询接口的实际开销（用户问「轮询是不是直接下载整个文件」时核对的）

**结论：不是。** 轮询与下载是两个独立接口：

- 轮询 `GET /api/admin/excel-tasks/{taskNo}` → `Result<ExcelTaskVO>`，纯 JSON 元数据，
  不含文件字节。`detail()` 只做 `getByTaskNo` 一次单行查询 + `toVO`。
- 下载 `GET /api/admin/excel-tasks/{taskNo}/download` 是独立接口，返回 `void`，
  用 `Files.copy(Path, OutputStream)` 流到响应，内存与文件大小无关。
  （刻意不用 `ResponseEntity<byte[]>` 也不异步派发，理由都写在 Controller 注释里。）

**新发现的一条（低，并入上面第 11~14 条同级）**：`toVO` 里 `isDownloadable` 对导出任务会调
`fileStorage.exists()` → `Files.isRegularFile`，**每次轮询都做一次磁盘 stat**。
更值得注意：`page()` 也对每行记录调 `toVO`，所以任务列表页一页 10 行 = 10 次磁盘 stat。
量级很小（本地 stat 是微秒级），但属于「为了算一个派生字段而碰 I/O」，
若以后存储换成对象存储（每次 exists = 一次 HTTP HEAD），这个开销就不能忽略了。
修法：列表页不算 `downloadable`（置 null），或把存在性判断改成「按 file_path 非空 + 状态成功」。

### 前端对接口径（用户问「上传和下载都要轮询吗」时梳理的）

**结论：上传和下载都只发生一次，只有「任务进度」需要轮询。**
一次完整流程 = 1 次上传/提交 + N 次轮询 + 1 次下载。

核对出的完整接口面（写进了新参考文档）：

- 导入：`POST /api/admin/users/import`（`system:user:import`）、
  `POST /api/admin/products/import`（`product:product:import`），都是 multipart，字段名 `file`
- 导出：`POST /api/admin/{users,products,orders,operation-logs}/export`，
  权限码分别是 `system:user:list` / `product:product:list` / `order:order:list` / `system:log:list`
  —— **导出的权限码是「列表」权限，没有单独的 export 权限**
- 任务中心：`GET /api/admin/excel-tasks`、`/{taskNo}`、`/{taskNo}/download`，都是 `isAuthenticated()`

**下载侧的三个坑（前两个是事实，第三个是推论，已核对代码）**：

1. **不能用 `<a href>` / `window.open()`** —— 已确认 `JwtAuthenticationFilter` 只读
   `Authorization` 头（`header.startsWith(BEARER_PREFIX)`），不支持 query param / Cookie。
   浏览器导航请求不带这个头 → 401。必须 fetch + blob。
2. **文件名是 RFC 5987 的 `filename*=UTF-8''...`**，要按带星号的那个正则解析 + `decodeURIComponent`。
3. **失败时 HTTP 仍是 200，但响应体是 JSON，且 `Content-Disposition: attachment` 还挂着** ——
   `GlobalExceptionHandler` 对 `BusinessException` 没有 `@ResponseStatus`，所以是 200 + JSON；
   而 Controller 是先 `setContentType`/`setContentDisposition` 再抛异常，响应头不会被清掉。
   前端 `responseType:'blob'` 会把 JSON 当文件收下，**不检查 `blob.type` 就会下载到一个装着错误信息的「xlsx」**。

### 补充：导入的终态语义（用户复述流程时暴露的误解）

用户复述的流程是「导入进任务中心，执行完就导入成功了」——**这处是错的**，已在
`references/frontend-integration.md` 里补了一节专门纠正：

**行级失败不改变任务成功状态。** 500 行里 3 行坏，任务 `status=2`（成功）且 `failRows=3`。
所以「执行完」对导入有三种结局：

| 结局 | status | failRows | 下载按钮 |
|---|---|---|---|
| 全部成功 | 2 | 0 | **不显示**（`downloadable=false`） |
| **部分成功** | **2** | **>0** | 显示，下的是**失败明细** |
| 完全失败 | 3 | 视情况 | failRows>0 时显示 |

前端文案必须区分前两种，不能统一弹「导入成功」。已给出判断代码片段。

另一个关键区分：**导入的下载按钮 ≠ 导出结果**。导出下的是「我要的数据」，
导入下的是「哪些行错了、为什么」，用户改完重传。

另核对确认：失败明细是**按需从 `excel_task_error` 表流式拼出来的**，不落盘，
且 `ExcelTaskCleanupTask` 只做 `failStaleTasks()` + `cleanupExpiredFiles()`，
**不删任务记录也不删明细**，所以 24 小时保留期只影响导出结果文件的磁盘文件，
导入的失败明细随时可下。
