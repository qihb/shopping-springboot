   根因：「羊毛账号剔除 3,465 条」取的是**全表**数量，而时间窗**已先砍掉其中 1,766 条**，重复计数。

### 技术栈现状与已识别缺口（用户追问后核查）

**技术栈**：Spring `@Scheduled` + 手写 Redis 锁（`setIfAbsent` + Lua 校验持有者），
**未引入** Quartz / XXL-JOB / ShedLock / Redisson（已全项目 grep 确认；quartz 仅出现在 Spring Boot 自动配置的负面匹配日志里）。
全项目只有 2 个定时任务：`OrderTimeoutTask`（fixedDelay 60s）、`CartRecallTask`。

**已识别的两个缺口（尚未修，用户未确认）**：
1. **无失败告警** —— 失败只打一行 `log.error`，没人看日志 = 静默失败。最轻的补法：`saveTaskLog` 里判断 `status==0` 发企微/钉钉 webhook。
2. **`stats_task_log` 无查询接口** —— `AdminRecallController` 只有 `/summary` `/products` `/targets` `/build`，
   运营看不到「今天跑了没、成功没」。建议补 `GET /api/admin/stats/recall/task-logs`。

**其他已知局限**：无自动重试（失败等第二天 4 点）、无分片（单实例跑全量）、锁是手写的。
补偿机制：幂等（`deletePending` 只删 status=0 再重建）→ 可随时安全重跑，这是主要兜底。

**日志查看位置**：`logs/spring-shop.log`（全量，按天滚动保留 30 天）、`logs/spring-shop-error.log`（ERROR 单独归档）；

## 定时任务平台化 + 重跑机制 — 技术方案（未落地代码，待用户拍板）

**用户指令**：「后面还会有更多任务，给我出一份相关的技术报告选项，支撑后面更多任务跑，还要有任务重跑机制」。

**产出**：`docs/superpowers/plans/2026-10-03-scheduled-task-platform-options.md`（7 个调度方案对比 + 重跑机制设计 + 待拍板 7 项）。

**关键调研结论（复用价值高）**：
- **两个定时任务能力集完全不同**，证明基础设施缺抽象层：
  | | `OrderTimeoutTask`（62 行） | `CartRecallTask`（197 行） |
  |---|---|---|
  | 分布式锁 | ❌ 无 | ✅ Redis 锁 |
  | 任务日志 | ❌ 只有 log.error | ✅ stats_task_log |
  | 开关 / 手动触发 | ❌ 无 | ✅ 有 |
  新增一个任务约 **150 行样板代码**，业务逻辑只占 ~20 行。
- **本方案的核心认知：不是所有任务都能重跑**。必须先分类：
  A 全量重建型 / B 按天快照型 / C 状态机推进型（均可重跑）vs **D 副作用型（发券/发短信，默认禁止重跑）**。
  四种幂等策略：`DELETE_INSERT` / `UPSERT` / `CONDITIONAL` / `NONE`。
- **`bizDateAware` 是最关键的开关** —— 任务签名必须统一为 `execute(LocalDate bizDate)`，
  不参数化业务日期就只能重跑「今天」，历史补数无从谈起。这是当前设计最大的结构性缺陷。
- **六道重跑护栏**：bizDate 必传 / 唯一键 `uk_task_biz_attempt` 防并发 / 窗口 ≤30 天 / 每日 ≤3 次 / 不可重跑任务拒绝 / `task:run` ≠ `task:rerun` 权限分离。
- **自动重试只对瞬时异常生效**：`QueryTimeoutException`/`TransientDataAccessException`/死锁/Redis 抖动 → 重试；
  `BusinessException`/参数错误/脏数据 → **不重试**（重试也是白试）。退避 1min→5min→15min，上限 3 次。
- **「产出 0 行」告警最容易被忽略但最有价值** —— 任务「成功」了但没产出数据，比跑失败更隐蔽。
- **推荐方案 B（自研轻量层）**：单体应用 + 任务数 10 上下，上 XXL-JOB 的运维成本 > 收益。
  自研必须克制，只做统一锁/日志/重跑/告警四件事；触到编排/分片/GLUE 边界就该迁 XXL-JOB（触发条件：任务数 >15）。
- **`OrderTimeoutTask` 迁移时应保持不加锁**（声明 `lockStrategy = NONE`）—— 它 fixedDelay 60s、处理量小、
  `systemCancel` 是条件更新天然幂等，加锁反而可能因锁竞争影响取消时效。**这也验证抽象层必须支持「按任务选策略」**。
- **`OrderTimeoutTask` 是 `bizDateAware = false` 的「持续扫描」型** —— 抽象层必须同时容纳「按天跑批」和「持续扫描」两种形态，
  否则说明抽象错了。

**待拍板 7 项**：调度框架 / 锁实现（手写 Redis vs ShedLock）/ 不可重跑默认值 / 重跑窗口 / 告警通道（需 webhook 地址）/ 是否本期迁 OrderTimeoutTask / 模块归属（建议新建 `spring-shop-task`）。
