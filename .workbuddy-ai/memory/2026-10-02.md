## ⚠️ 工具踩坑（重要，后续编辑务必注意）
1. **同一文件在一次消息里批量 Edit 会丢失部分改动**（报告 success 但内容未落盘）。结论：对同一文件的多处修改必须**逐条、分消息**执行，并在改完用 Grep 复核。
2. **Edit/Write 偶发把已存在文件按 GBK 落盘**（AuthController.java 曾整文件变 GBK，导致 `file` 显示非 UTF-8）。
   修复：`python3 -c "p.write_bytes(p.read_bytes().decode('gbk').encode('utf-8'))"`。
   每次改完建议跑一次 UTF-8 校验（decode utf-8 + 检查「中文后紧跟 ?」的丢字模式）。

**需求**：每天凌晨 4 点跑全量购物车数据做分析，排出前 100 商品。

**产出**：`docs/superpowers/plans/2026-10-02-cart-hot-rank-job.md`（方案 + 注意事项 + 4 个待决策点）。**状态：等待用户拍板后再写代码。**

**关键调研结论（后续复用价值高）**：
- `@EnableScheduling` 已在 `SpringShopApplication` 上；已有定时任务先例 `order/task/OrderTimeoutTask.java`（`@Scheduled(fixedDelay=60_000)`）
- **`cart_item` 是状态表不是事件表**：同 SKU 加购累加数量（`CartServiceImpl.add()`），下单/清空/删勾选走**物理删除**；`CartItem` 实体未映射 `is_deleted`（无 `@TableLogic`，MyBatis-Plus 不会自动拼该条件，手写 XML SQL 需自己加）→ 跑批只能看到「当前快照」，加购→下单的链路数据已被删除
- `cart_item` 仅有 `uk_user_sku(user_id, sku_id)` + 主键，**无 sku_id 单独索引** → `GROUP BY sku_id` 会全表扫 + filesort
- 项目目前**没有任何 XML Mapper**（`resources/mapper/**` 为空），复杂 SQL 走 XML 是新引入的能力
- 错误码已占用 0-99 / 1000 / 2000 / 3000 / 4000 / 5000 / 6000 段 → 统计模块建议申请 7000~7999，并回填 AGENTS.md 错误码表

- `application-test.yml` 用 H2（MODE=MySQL）+ `db/migration-test`

**方案要点**：
- 建议新建 `spring-shop-stats` 模块（依赖 common + cart + product），遵循 AGENTS.md 新模块约定

## 需求修订：加购未买召回发券（同日下午）

**用户澄清真实目标**：不是做热度榜，而是「统计购物车里没买的，给用户发优惠价刺激购买」。热度榜降级为「选品」中间步骤。

**新产出**：`docs/superpowers/plans/2026-10-02-cart-recall-coupon.md`（旧文档已加修订说明指向它）

**关键结论（复用价值高）**：
- ✅ **口径天然吻合**：`OrderServiceImpl.create():139-141` 下单成功后物理删除已勾选 cart_item，所以 `cart_item` 剩下的按定义就是「加购未买」集合；且 `create_time` 只被 insert 写入、改数量/勾选只刷 `update_time`（`updateById`），因此 `create_time` 恰好是准确的「首次加购时刻」，可直接做时间窗过滤
- ❌ **三块基础设施全缺**：① 无优惠券体系（`OrderServiceImpl:124` 注释「暂无优惠券/运费…（YAGNI）」）② 无优惠计算（`setPayAmount(totalAmount)`，orders 无 discount_amount 字段）③ 无消息触达（全项目 grep 零命中）；用户侧有 `User.phone`（**可空**）+ `openid`
- ⚠️ **最大盲区：无归因能力** —— 下单即删记录，导致「发券→转化」链路无法闭环，核销率/ROI 算不出来。必须补 `cart_add_log` 加购流水 + `coupon_grant` 发券记录，且**埋点越早越好（只能记录埋点之后的行为）**
- 💡 **选品洞察**：单纯按加购人数排 TOP100 选出的是热门商品，给它打折是白送利润；真正值得发券的是**弃购率高**的（很多人加购、很少人成交 = 卡在价格上）。`弃购率 = 加购未买用户数 / (加购未买用户数 + 已成交用户数)`，两个数据源都在（cart_item + order_item）
- **金额链路是最高风险区**：改下单用券会波及 `total_amount`/`pay_amount`/`discount_amount`、`pay_record.amount`、退款，算错即资损，需单独立项 + 对账测试
- **建议分期**：Phase1 只圈人（零外部风险，先验证规模与价值）→ Phase2 券能力 + 加购流水埋点 → Phase3 触达（短信/订阅消息，外部依赖 + 合规）→ Phase4 归因调优
- **商业风险**：给加购未买的人发券 = 训练用户「加购等券」，长期拉低客单价。缓解：券面额小、限时 24h、限品、每人 30 天 ≤2 次、不公开规则
- 待拍板：本期范围（只圈人/做到发券）、券模型（商品定向券/千人千券）、选品口径、触达通道、加购流水是否本期做
