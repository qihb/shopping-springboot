## 追加（15:10）：锁数量 + 增减日志的设计方案（只输出，未落文件）

用户问「库存表按 SKU 记，后续的锁数量怎么设计、增减日志怎么记，给一个设计方案」。
**按第一原则「讲讲怎么做 ⇒ 只输出计划」，本次只在对话里给设计，未改任何仓库文件**
（计划文档项 3 目前只写了流水表、**还没写锁数量**，待用户确认后再合并）。

### 一、锁数量：加一个计数器，不拆表

- 在 `product_sku` 上加 **`locked_stock INT NOT NULL DEFAULT 0`**（不新建表，单仓够用）。
- 三量：`stock`（在库实物量）/ `locked_stock`（未付款订单锁定）/ `available = stock − locked_stock`（可售）。
- **不变量**：`0 ≤ locked_stock ≤ stock`。前端展示、下单校验都用 `available`。
- ⚠️ **语义变化**：`stock` 由现在的「可售（下单即扣）」变成「实物在库」——前端要跟着改。
- 事件作用：下单 `locked += n`（条件 `stock − locked ≥ n`）；支付 `stock −= n, locked −= n`；
  取消/超时 `locked −= n`；后台调整改 `stock`（须 `≥ locked`）；导入初始化 `stock += n`。
- 并发靠条件 UPDATE（0 行即失败），与现有 `deductStock` 同型，全部带 `version = version + 1`。

### 二、增减日志：`stock_log` 每行同时记两个计数器的前后值

- 列：`sku_id / product_id / change_type / stock_before / stock_after / locked_before / locked_after /
  biz_no / operator_id / remark / create_time`。
- **append-only**，不设 `is_deleted` / `version`（是「账」不是「状态」）。
- 存前后值而非只存 `change_qty`：可逐条核对（上一行 `after` == 下一行 `before`）。
- `change_type`：1 下单锁定 / 2 支付出库 / 3 取消释放 / 4 后台调整 / 5 导入初始化。
- ⚠️ **MySQL UPDATE 不返回旧值** ⇒ **同一事务内**：先条件 UPDATE → 成功后 `selectById` 拿 `after`
  → `before = after ∓ n`；**流水与业务更新同事务提交**（保证「改了库存必有账」）。

### 三、落地要点

- **Flyway V9**：`ALTER TABLE product_sku ADD COLUMN locked_stock ...` + `CREATE TABLE stock_log`；
  主库 + `migration-test` 双侧同步、索引名全局唯一（CI 红线）。
- 改动调用点（本轮最重）：`OrderServiceImpl.create()`（扣 stock → 锁 locked）、支付 `markPaid`（新增出库）、
  取消/超时（`restoreStock` → 释放 locked）、后台 `saveSkus`、导入初始化。
- `StockLogService` 放 `spring-shop-product`，order/pay 已依赖 product ⇒ 依赖方向不变。
- 对账：最新一条的 `stock_after` == 当前 `stock`；`locked_after` == 当前 `locked_stock`。

## 16:10 补一个第 3 阶段自己引入的缓存一致性漏洞（已修）

### 问题

第 3 阶段把「可售量」放进了商品详情 VO（`ProductQueryServiceImpl.toSkuVO` 读 `availableMap`），
而详情**整体**被缓存在 `product:detail:{id}`（TTL 30 分钟 + 随机抖动）。

于是「凡改变可售量的库存变更都必须失效详情缓存」。逐个核对四条库存写路径后：

| 写路径 | 可售量变？ | 谁失效 | 结论 |
|---|---|---|---|
| `lock`（下单） | 变 | `OrderServiceImpl.create()` 已有 | ✅ 无需动 |
| `release`（取消/超时） | 变 | `OrderServiceImpl.cancel/systemCancel` 已有 | ✅ 无需动 |
| `outbound`（支付出库） | **不变** | —— | ✅ 无需动（见下） |
| **`adjust`（后台调库存）** | 变 | **没有人** | ❌ **漏洞** |

`adjust` 是第 2 阶段新加的后台接口，没有调用方兜底 ⇒ 后台改完在库量，
前台详情页最多 31 分钟仍显示旧的可售量。**这是我自己引入的**。

### `outbound` 不需要失效 —— 这是个值得记住的不变量

可售量 = `stock − locked_stock`；出库时**两者同时减 q** ⇒ 差值恒等：
`(S−q) − (L−q) = S − L`。语义上也说得通：支付只是把「锁定」转成「已售」，
那 q 本来就没对其他人可售。
⇒ **不要为了「对称」给出库加一次失效**（会平白给支付热路径引入 Redis 依赖）。
已写一条测试把这个「不做」钉住：`InventoryServiceImplTest#outbound_shouldNotEvictDetailCache_becauseAvailableIsInvariant`。

### 修法

`InventoryServiceImpl` 注入 `StringRedisTemplate`，在 `adjust()` 落完流水后
`delete(RedisKeys.productDetail(productId))`（`productId` 用它已有的 `resolveProductId(skuId)` 解析，
所以 key 里是 productId 不是 skuId）。直删不吞异常，与 `ProductManageServiceImpl` 失效详情缓存的写法一致。

### 测试

- 单测：`adjust` 成功 ⇒ `verify(delete(productDetail(productId)))`；`adjust` 失败 ⇒ `verifyNoInteractions`（失败不该白白失效）；
  新增出库不失效的用例。
- 集成测试：`InventoryIntegrationTest#adjust_shouldWriteOperatorAndRemark` 加断言，
  **顺带验证 key 里用的是 SKU 解析出的 productId**（写成 skuId 就永远删不掉缓存）。

### 🔴 关键决策：**不改 V2、不改 V9**

原本的计划是「顺手把 V2 里那行列定义也删掉，让新库直接不带这列」——**这是错的，已纠正**：

`application.yml` 的 Flyway 用默认 `validate-on-migrate`，**已发布脚本的校验和写进了
`flyway_schema_history`**。动 V2 一个字节 ⇒ 所有已经跑到 V9 的库（含本机 dev）**启动即校验失败**。
正确做法是**纯增量**：V2 建列 → V9 回填 → V10 删列，新库与老库最终结构一致。

### 两个设计点

1. **`SkuDraft` 记录**：库存不能再挂在实体上，但建 `inventory` 行必须在 SKU 拿到自增 id
   **之后**（`insertBatch` 是自定义 `@Insert`，不回填主键，得按 `sku_code` 回查）。
   中间这段路需要一个地方存「这行想要的库存」⇒ 用 `record SkuDraft(ProductSku sku, int stock)`。
2. **DROP 前的一致性检查写进脚本头注释，没写进脚本**：脚本要同时跑 MySQL 8 与 H2，
   「不一致就报错中止」需要 `SIGNAL`/存储过程，两套方言写法不同。校验交给发布流程。

### 验证

- `mvn clean test` → **BUILD SUCCESS，409 用例**（common 38 / user 17 / admin 28 / product 95 /
  cart 38 / order 33 / pay 7 / stats 10 / web 143）—— **用例数与 V10 前一致**（本轮只删字段、不删测试）。
- H2 上 V10 确实生效：`RecallIntegrationTest.seedProduct` 里带 `stock` 的 INSERT 报
  `BadSqlGrammar`，去掉后全绿 ⇒ 列真的没了。

### 踩到的坑（重要，已写进 MEMORY.md）

**同一文件的多处 `Edit` 不能放在同一条消息里并行发** —— 本轮把 `ProductSku.java`（3 处）、

## 18:40 项 1a 落地：定时任务执行日志查询接口

### 补的是什么缺口

`stats_task_log` **有写无读**：`CartRecallTask` 每天把执行结果写进表，

| 新增 | `stats/dto/StatsTaskLogPageQuery`（继承 `PageQuery`） |

| 新增 | `web` 集成测试 `AdminTaskLogQueryIntegrationTest`（7 用例） |

### 两处实现取舍

1. **按「执行时间」`start_time` 过滤，不按「业务日期」`stat_date`**：
   运营问的是「这几天任务跑没跑」＝执行时刻语义；而且表上只有
   `idx_stats_task_log_name_time (task_name, start_time)` 这一个索引，按 `stat_date` 过滤用不上它。
   手动补数（为过去的 `stat_date` 重跑）也只在执行时间上看得见 —— 按业务日期过滤反而会把补数记录藏起来。
2. **日期用半开区间 `[startDate 00:00, endDate+1 00:00)`**，不写 `endDate 23:59:59`：
   后者要猜列精度（这里是 DATETIME，无小数秒），且会漏掉当天最后一秒的记录。
   定时任务正好在凌晨触发，运营查「昨天」时最容易踩到这个边界。
   集成测试专门钉住「次日 0 点整的记录不算进来」。

### 1b（失败告警）明确不做

真正的告警需要外部 webhook 地址（企微/钉钉），没有地址就只能做「log.warn」这种假告警，
和现在的 `log.error` 没有本质区别。计划里保留设计作留档。
